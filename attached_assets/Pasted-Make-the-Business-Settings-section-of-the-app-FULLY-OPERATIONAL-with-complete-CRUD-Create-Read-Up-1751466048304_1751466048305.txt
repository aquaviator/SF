Make the Business Settings section of the app FULLY OPERATIONAL with complete CRUD (Create, Read, Update, Delete) for all business configuration data.

All UI controls in Business Settings must actually work, trigger real backend/API calls, and persist changes. No stubs, no placeholders, no “fake success” messages. Any fields/data that are not yet implemented must be clearly marked as such, with a modal stating "This is not wired up yet."

Functional Requirements
1. Business Profile (Full CRUD)
User can create, view, edit, and delete all business profile details:

Business Name

Owner name/contact

Address and contact details

Business logo (file upload)

Owner profile picture (file upload)

Other metadata as currently in the UI

All changes must persist to the database and update all relevant UI immediately after save.

UI should update dynamically (e.g. sidebar name/logo, profile summary, etc) after changes.

2. Job Roles (Full CRUD)
User can add, edit, delete, and view job roles (e.g., Manager, Chef, Waitstaff).

CRUD operations must update the database and refresh any dropdowns/UI using job roles.

No hardcoded/test roles — all roles are managed via this CRUD.

3. Locations (NEW: Full CRUD)
Add a new “Locations” section to Business Settings (e.g., FOH, Restaurant, Kitchen, Bar, etc).

User can create, view, edit, and delete locations.

Locations must be stored persistently and available dynamically in dropdowns across the app (e.g., when scheduling shifts).

UI must update live after CRUD actions.

No test or placeholder data for locations.

4. Departments (Full CRUD)
If “Departments” is a separate concept from Locations, add full CRUD for Departments as well.

Department dropdowns must be populated only from this CRUD source.

5. Operating Hours (Full CRUD)
User can set operating hours (open/close times) for each day of the week.

User can add, edit, delete, view operating hour entries.

Persist all changes and ensure UI always displays the current, accurate state after change.

6. Error Handling & Placeholders
If a button or form is not wired up yet, clicking it must open a modal stating:

"This action is not implemented yet. (Placeholder – no API call made)"

Any field/section in the UI that’s displaying hardcoded/test/demo data must be marked with:

"(Placeholder)"

All other controls must trigger actual backend calls and persist data.

7. Audit & Feedback
Every CRUD operation should provide visual confirmation of what was changed, and reflect those changes on reload.

If a field/section is not yet implemented, this must be visually obvious.

Bug Fixes (From Testing & Errors)
Fix any button in Business Settings that has no network activity.

Every action should have an API request, or else a modal explaining that it is not implemented yet.

Fix cases where alerts show “updated” but the data does not persist.

Fix dynamic updates in UI: If a profile or logo is changed, it should reflect everywhere in the UI instantly.

Fix Roles/Departments/Locations: All dropdowns and selectors should be fully dynamic and sourced from CRUD data.

Ensure all test/demo/placeholder values are either real, or explicitly marked as such.

Extra: Testing & Verification
After implementation, produce a checklist of all CRUD controls/fields.

Note whether each is fully functional, placeholder, or not yet implemented.

For each CRUD action, describe what API is called, what database change occurs, and how the UI responds (including on reload).
