Below is an end-to-end description of how our Shift Swap workflow operates, and exactly how and when it escalates according to our configurable Shift Policies (notice windows, cancellation deadlines, strike thresholds, etc.).

1. Initiating a Swap Request (Staff → System)
Staff action

On their My Shifts page, a staff member clicks “Request Swap” on an upcoming shift.

The UI fires a POST to /api/shift-actions/request-swap with payload

json

{
  "tenantId": "...",
  "shiftId": 123,
  "requestedBy": 42,         // staff userId
  "reason": "Family emergency"
}

📨 SWAP_REQUESTED { shiftId:123, userId:42, timestamp:… }
Policy Check

The backend shiftService.requestSwap() fetches the business’s active Shift Policy (from shift_policies):

minNoticeHours (e.g. 24h)

cancellationDeadlineHours (e.g. 4h)

maxStrikePoints, etc.

It computes timeUntilStart = shift.startTime – now().

2. Routing the Request → Peer or Escalation
If timeUntilStart ≥ minNoticeHours
→ Peer-to-Peer Swap

Mark swap request “Open”, notify all qualified co-workers in the same role/department via in-app notifications & email.

They see it under Swap Requests → Available.

If timeUntilStart < minNoticeHours but timeUntilStart ≥ cancellationDeadlineHours
→ Escalate to Management

Mark request “Escalated”, notify the business owner/manager on Live Operations → Escalations.

Staff cannot self-approve; only manager can reassign or approve.

If timeUntilStart < cancellationDeadlineHours
→ Automatic Strike & Deny Swap

Deny swap outright (403 Forbidden) because it’s too close to shift start.

Assign a Late Cancellation Strike (1 point) via our strike‐service.

Notify staff of denied request and strike.

3. Peer Swap Approval Flow
Another staff member clicks “Accept Swap” on the open request.

Backend verifies they don’t exceed strike limits (canClaimShift()) and updates both assignments:

Original user’s assignment unassigned

New user’s assignment created (status = “confirmed”)

4. Manager Escalation Flow
Manager visits Live Operations → Escalations panel.

They see all escalated requests with columns:
| Shift | Requested By | Time Until Start | Policy Notice | Action |

They can “Approve” or “Reassign…”:

Approve: same as peer-approval.

Reassign: opens shift-assignment modal to pick a replacement.

5. Unclaimed Open Swaps
We schedule a deadline for each open swap (now + swapExpiryHours from policy).

If no one accepts by that deadline:

Automatically escalate to management (if within policy window).

If outside even escalation window, mark shift “Unfilled” and flag under Live Operations → Coverage Gaps.

6. Summary of Escalation Rules
Condition	Outcome
timeUntilStart ≥ minNotice	Peer-to-peer swap, open to team
cancellationDeadline ≤ timeUntilStart < minNotice	Automate escalate to manager
timeUntilStart < cancellationDeadline	Deny swap + assign late-cancel strike
No peer accept by swap expiry	Escalate to manager → if too late, coverage gap flag

All of these steps are driven by the Shift Policy for that business, enabling truly flexible, policy-driven swap management that keeps both staff and owners in sync.
